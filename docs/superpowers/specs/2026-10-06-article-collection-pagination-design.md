# 文章与收藏列表分页设计

## 目标

为文章列表和我的收藏列表增加完整的下拉刷新与上拉分页能力。两个列表统一使用 Flutter 官方 `RefreshIndicator` 实现下拉刷新，使用 `infinite_scroll_pagination` 实现滚动触底、分页状态展示和失败重试，并通过 Riverpod 管理网络请求与业务状态。每次请求固定读取 10 条数据。

## 范围

- 文章列表请求 `/article/list/{page}/json`，页码从 0 开始。
- 收藏列表请求 `/lg/collect/list/{page}/json`，页码从 0 开始。
- 两个接口都传递 `page_size=10`。
- 支持首次加载、下拉刷新、自动加载下一页、下一页失败重试和没有更多数据提示。
- 保留现有登录、注册、收藏、取消收藏、路由和会话隔离行为。
- 不增加本地分页缓存、离线浏览、列表筛选或预加载配置页面。
- 所有 Git 提交信息继续使用中文，并按独立功能拆分。

## 技术选择

### 下拉刷新

继续使用 Flutter SDK 自带的 `RefreshIndicator`。它负责识别下拉手势和展示刷新动画，实际刷新操作由 Riverpod 控制器执行。这样不需要为标准下拉刷新额外引入依赖，也便于 Widget 测试。

### 上拉加载更多

引入 `infinite_scroll_pagination ^5.1.1`，使用 `PagedListView`、`PagingState` 和 `PagedChildBuilderDelegate`：

- `PagedListView` 监听列表位置，在接近末尾时请求下一页。
- `PagingState` 向页面描述已加载的数据页、当前加载状态、错误和是否还有下一页。
- `PagedChildBuilderDelegate` 统一构建首次加载、首次错误、空列表、下一页加载、下一页错误和列表结束提示。

分页包只负责滚动与展示。页码推进、接口调用、文章去重、刷新作废旧请求和账号隔离仍放在 Riverpod 控制器中，保证业务规则可以独立测试。

## 数据模型与接口

新增 `ArticlePage` 数据模型，继续采用 `freezed` 与 `json_serializable` 组合，解析接口 `data` 中的字段：

- `datas`：当前页文章。
- `curPage`：服务端当前页编号。
- `pageCount`：总页数。
- `over`：服务端是否已经到最后一页。

`ArticlePage.hasMore` 根据 `over` 和页数信息判断是否还有下一页。业务请求页码使用客户端保存的 0 基页码推进，避免服务端 `curPage` 展示规则影响下一次 URL。

文章与收藏 Repository 分别改为接收 `page` 和 `pageSize`，返回 `ArticlePage`。默认且实际调用的 `pageSize` 均为常量 10。服务层继续把业务错误、HTTP 错误、连接错误和解析错误转换为现有的可读异常。

## 分页状态

新增 Freezed `ArticleListState`，收藏列表扩展现有 Freezed `CollectionState`。两个状态都包含：

- 已成功加载的分页数据。
- 下一次请求的 0 基页码。
- 是否还有下一页。
- 当前是否正在请求。
- 当前分页错误。

分页数据按页保存，以便直接转换为 `PagingState<int, Article>`。页面展示时再展开为一维文章列表。收藏状态继续保留账号标识、已确认收藏状态、正在收藏的文章键和本地修改版本。

首次加载和下一页加载共用一个互斥请求入口。已有请求未结束时忽略重复的加载更多触发；没有下一页时也不会发送网络请求。

## 数据流

### 首次加载

1. 控制器以第 0 页和每页 10 条发起请求。
2. 成功后保存第一页、设置下一页为 1，并依据 `ArticlePage.hasMore` 更新结束状态。
3. 失败时交给分页列表展示全屏错误和重试按钮。

### 上拉加载更多

1. `PagedListView` 接近末尾时调用控制器的 `loadNextPage`。
2. 控制器检查登录身份、请求互斥状态和 `hasMore`。
3. 成功后按文章业务编号去重并追加新页，再把下一页页码加一。
4. 失败时保留全部已有文章和当前页码，在列表底部显示“加载失败，点击重试”。点击后重试同一页。
5. 没有下一页时在列表底部显示“已经到底了”。

### 下拉刷新

1. `RefreshIndicator` 调用控制器的 `refresh`。
2. 控制器递增请求世代，使正在进行的旧请求结果失效，然后重新请求第 0 页。
3. 成功后用新第一页替换全部旧分页数据，下一页重新设为 1。
4. 失败时保留用户当前可见的数据，并通过 SnackBar 提示；如果尚无数据，则由分页列表展示首次错误页面。

每次网络请求完成后都核对请求世代。旧的加载更多请求即使晚于刷新返回，也不能把过期数据追加到新列表。

## 文章去重

文章列表按 `Article.id` 去重。收藏列表优先按 `originId` 表示的原文章编号去重；缺少有效 `originId` 时使用收藏记录 `id`。新页中已经存在的文章不再追加，但下一页页码仍正常推进，防止接口重复数据导致同一页被无限请求。

## 收藏列表一致性

收藏分页继续遵守现有账号周期和本地收藏修改保护：

- 请求发出时记录账号身份、登录周期、请求世代和本地修改版本。
- 退出登录、切换账号、同账号重新登录或下拉刷新后，旧请求结果不能写入当前状态。
- 加载下一页只把本页返回的文章标记为已收藏，不会因为文章未出现在当前页而把前面页面的收藏状态改为未收藏。
- 刷新第一页时替换可见分页数据；如果服务端明确表示没有下一页，则当前响应代表完整收藏集合，可以清理不存在的旧确认状态。
- 如果刷新后的第一页仍有后续页面，则保留尚未重新加载到的旧收藏确认状态，避免把仍位于后续页面的文章错误显示为未收藏。
- 请求期间发生的收藏或取消收藏，以本地成功操作的较新版本为准。
- 收藏页取消成功后，从所有已加载页移除对应记录；后续分页仍可继续加载。
- 普通文章刚收藏成功后，进入收藏页会先等待正在执行的收藏请求，再刷新第 0 页取得服务端收藏记录编号。

## 页面状态

文章列表和收藏列表使用相同的中文状态：

- 首次加载：页面中央进度指示器。
- 首次失败：错误信息和“重试”按钮。
- 空数据：保留各页面现有空状态，并允许下拉刷新。
- 加载下一页：列表底部小型进度指示器。
- 下一页失败：列表底部“加载失败，点击重试”。
- 全部加载完成：非空列表底部显示“已经到底了”。

文章卡片、收藏按钮、侧边栏和详情页跳转保持现有交互。

## 测试策略

按测试驱动方式实现：

1. 数据模型测试覆盖分页字段解析和 `hasMore`。
2. 服务测试覆盖动态页码、`page_size=10`、文章解析和收藏文章标记。
3. 文章控制器测试覆盖首次加载、追加、跨页去重、失败后同页重试、没有更多数据、刷新重置和过期请求丢弃。
4. 收藏控制器测试覆盖相同分页行为，并覆盖账号切换、登录周期、本地收藏操作与分页请求并发。
5. Widget 测试覆盖下拉刷新、触底加载、底部加载、分页错误重试和结束提示。
6. 回归运行完整 `flutter test`、`flutter analyze` 和 iOS 模拟器构建。

## 验收标准

1. 文章列表和收藏列表首次只请求第 0 页，每页固定 10 条。
2. 两个页面都能通过下拉刷新重新加载第 0 页。
3. 两个页面滚动接近底部时自动加载下一页，且不会并发重复请求。
4. 下一页失败不会清空已有内容，可以在底部重试同一页。
5. 接口没有更多数据后停止请求，并显示“已经到底了”。
6. 刷新、登录变化和收藏操作并发时不会出现重复文章、过期数据或跨账号数据。
7. 完整测试、静态检查和 iOS 模拟器构建全部通过。
